# 09. Разработка и проверки

## Команды

```bash
node --test                          # 150+ тестов: хуки, установщик, скрипты, манифесты
node scripts/validate-skills.mjs      # скиллы: frontmatter, имена, размеры, ссылки, кейсы роутинга
node scripts/check-tokens.mjs         # бюджет постоянного контекста
node scripts/render-diagrams.mjs      # перерисовать PNG из docs/*/internals/diagrams
ROUTING_API_KEY=... node scripts/eval-routing.mjs --endpoint <url> --model <id>
```

Зависимостей нет: `node --test` — встроенный раннер Node.

## Тесты

| Файл | Что проверяет |
|---|---|
| `entry.test.mjs` | точка входа: не Maven-проект, битый JSON, неизвестное событие |
| `io.test.mjs` | папка сессии, `normalizeTool` для трёх харнессов, состояние, настройки |
| `root.test.mjs` | поиск корня Maven: `src/`, модуль, git-корень над `backend/`, две подпапки |
| `rules.test.mjs` | каждое правило ловит и не ловит, текст сообщения |
| `pre.test.mjs` | `PreToolUse`: блок новых, legacy не мешает, G1, G2, S1, S2 |
| `post.test.mjs` | `PostToolUse`: замечания, правила роли один раз |
| `session.test.mjs` | паспорт, якорь, восстановление после сжатия |
| `anchor.test.mjs` | короткие тексты, учёт нарушений и ролей, адаптивный якорь, нарушения в блоке восстановления, бюджеты |
| `stop.test.mjs` | предупреждение о контексте, компиляция, свои и чужие ошибки, лимит блоков, офлайн, `stopCompile` |
| `passport.test.mjs` | паспорт по фикстурам `tests/fixtures/poms/` |
| `version-aware.test.mjs` | советы по версии Boot и инструменту миграций |
| `state-race.test.mjs` | 20 параллельных процессов не теряют отметки |
| `review-fixes.test.mjs` | регрессии по итогам ревью: G1 и рост changelog, G2 для незакоммиченного, S2 по сегментам, `disable`, лимит блоков Stop, таймаут сборки, несколько модулей |
| `installer.test.mjs` | установка, слияние настроек, обновление, удаление байт в байт |
| `manifests.test.mjs` | манифесты трёх харнессов: подтверждённые события, единицы таймаутов, `PostToolUse` без shell |
| `scripts.test.mjs` | валидатор скиллов, бюджет токенов, роутинг |

Тесты вызывают `main(argv, stdin, env)` из `java-hooks.mjs` напрямую, без процесса.
Проекты создаются во временной папке (`tempProject`), входы харнессов — в
`tests/fixtures/inputs/`.

## Бюджет токенов

`scripts/check-tokens.mjs` (оценка: символы / 4):

| Что | Лимит | Почему |
|---|---|---|
| Роутер | 1500 | в каждой сессии |
| Якорь | 60 | в каждом сообщении GigaCode; худший случай — три самых длинных коротких текста |
| Блок восстановления | 500 | после каждого сжатия; худший случай — пять нарушенных правил с самыми длинными исправлениями |
| Правила роли | 120 | при первой записи роли |

## Гейт-фикстура

`tests/fixtures/gates-project` — Maven-проект (Boot 4, ArchUnit) с `CodeRulesTest` из
`java-quality-gates` и **одним нарушением на каждое из 13 правил**. CI проверяет, что
`mvn -B -ntp test` падает ровно с `Tests run: 13, Failures: 13`. Так видно, что каждое
ArchUnit-правило действительно ловит своё нарушение.

## Релизы

Каждый релиз получает тег `vX.Y.Z` на коммите `chore(release)`, тег пушится в remote: по этим
тегам уведомление об обновлении сравнивает версии. Версия поднимается в
`.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `.codex-plugin/plugin.json` и
`gigacode-extension.json` в том же коммите. Пре-релизные теги (`v1.0.0-rc1`) уведомление
игнорирует.

## Как добавить жёсткое или мягкое правило

1. Тест в `rules.test.mjs`: пример, который должен ловиться, и похожий, который не должен.
   Убедиться, что тест падает.
2. Текст в `RULES` (`rules.mjs`): `severity`, `short` (≤ 40 символов, для якоря), `message`,
   `fix`, `example`.
3. Проверка в `findViolations`. Помнить: строки и комментарии уже заменены пробелами.
4. Если правило жёсткое — тест в `pre.test.mjs`, что правка с ним блокируется, а правка
   рядом с legacy-нарушением — нет.
5. Упомянуть правило в роутере или в нужном скилле, если модель должна знать его заранее.
6. Таблицы в `docs/*/how-it-works.md` и [04-rules.md](04-rules.md).
7. Если правило проверяемо на байткоде — добавить и в `CodeRulesTest.java`, и нарушение
   в гейт-фикстуру (тогда число 13 в CI тоже меняется).

## Как добавить харнесс

1. Фикстуры входа в `tests/fixtures/inputs/`.
2. Имена инструментов и полей — в `normalizeTool` (`io.mjs`).
3. Манифест с регистрацией хуков и `--harness <имя>`.
4. Если харнесс иначе принимает ответ — ветка по `ctx.harness` в обработчике.
5. Тест в `manifests.test.mjs`.
