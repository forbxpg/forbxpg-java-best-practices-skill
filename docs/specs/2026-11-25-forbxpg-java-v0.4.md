# Спецификация: forbxpg-java v0.4 — уведомление об обновлении

Статус: **одобрена** 25.11.2026. Дата: 25.11.2026. Продолжает
[спецификацию v0.3](2026-11-24-forbxpg-java-v0.3.md).

## Решения гриля (25.11.2026)

1. При новой версии хук сообщает о ней, а агент **предлагает** команду обновления и
   выполняет её только после «да» пользователя (1б). Автообновления нет.
2. Проверка идёт в фоне, не чаще раза в сутки; результат показывается в следующей сессии (2а).
3. Последняя версия — наибольший git-тег `vX.Y.Z` на remote, откуда установлен скилл (3а).
4. Проверка включена по умолчанию, выключается в `forbxpg-java.json` (4а).
5. Коммиты и PR — без строк об авторстве ИИ.

Не входит: обновление установок через маркетплейс Claude Code (у Claude Code свой
механизм обновления плагинов), установки из zip без git, пре-релизные теги.

## 1. Откуда хук знает, что установлено

- **R-SRC-1.** Хук определяет источник установки по своему расположению:
  - **клон** (установка к себе через `install.mjs --scope user`, `--plugin-dir`,
    `gigacode extensions link`): папка `../../` от `hooks/lib` содержит `.git`. Версия —
    из `.claude-plugin/plugin.json` клона, remote — `git remote get-url origin`, папка для
    обновления — сам клон;
  - **установка в проект**: рядом лежит `install-receipt.json`. Версия и remote — из
    квитанции;
  - иначе (маркетплейс, zip) — проверки нет, ничего не выводится.
- **R-SRC-2.** `install.mjs --scope project` записывает в квитанцию `source.remote` —
  URL `origin` клона, из которого ставили, без логина и пароля в URL (`https://user:pass@`
  → `https://`). Путь к клону в квитанцию не пишется: квитанция коммитится в репозиторий
  команды.

## 2. Фоновая проверка

- **R-CHECK-1.** На `SessionStart` хук смотрит кэш
  `<tmp>/forbxpg-java/update-check/<sha1(remote)>.json` (`checkedAt`, `latest`, `error`).
  Если кэша нет или ему больше 24 часов, хук запускает отсоединённый процесс проверки и
  сразу продолжает — сессию проверка не задерживает.
- **R-CHECK-2.** Проверка: `git ls-remote --tags --refs <remote>` с таймаутом 5 с и
  `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`. Из тегов берётся наибольший
  `vX.Y.Z` (семвер, без суффиксов). Код не скачивается и ничего не запускается.
- **R-CHECK-3.** Ошибка (нет сети, Bitbucket просит пароль, таймаут) записывается в кэш с
  `checkedAt` — повтор через 24 часа; пользователю и модели ничего не сообщается.
- **R-CHECK-4.** Одновременно идёт не больше одной проверки на remote (файл-замок с
  истечением через 60 с).

## 3. Уведомление

- **R-NOTE-1.** Если `latest` из кэша больше установленной версии, `SessionStart`
  добавляет к своему выводу блок для модели:
  ```
  [forbxpg-java] Update available: 0.3.0 → 0.4.0.
  Tell the user once, in one line. If they agree, run: <команда>. Do not run it without their yes.
  ```
  Команда: для клона — `git -C "<папка клона>" pull --ff-only`; для установки в проект —
  «обновите клон forbxpg-java и запустите
  `node <клон>/install.mjs --agent <агент> --scope project --update`» (путь к клону
  модель спрашивает у пользователя).
- **R-NOTE-2.** В GigaCode тот же текст уходит и в `systemMessage`, чтобы пользователь
  видел его сам, даже если модель промолчит.
- **R-NOTE-3.** Уведомление идёт в каждой новой сессии, пока версия не обновится. В
  `UserPromptSubmit` и якорь оно не попадает.
  - S-NOTE-3a: WHEN установлена 0.3.0, в кэше `latest` 0.4.0 THEN `SessionStart` выводит
    блок с `0.3.0 → 0.4.0` и командой.
  - S-NOTE-3b: WHEN `latest` равна установленной или меньше THEN блока нет.
  - S-NOTE-3c: WHEN источник не определён (нет `.git`, нет квитанции) THEN ни проверки,
    ни блока.

## 4. Настройка и ручная проверка

- **R-CONF-1.** `forbxpg-java.json`: `"updateCheck": false` выключает и фоновую проверку, и
  уведомление.
- **R-CONF-2.** `node install.mjs --check` проверяет сразу (синхронно, тот же
  `ls-remote`) и печатает установленную и последнюю версию для клона, из которого
  запущен.

## 5. Релизы

- **R-REL-1.** Релизы помечаются тегами `vX.Y.Z`: проставить `v0.1.0`, `v0.2.0`, `v0.3.0` на
  их релизные коммиты; правило «тег на каждый релиз» — в `docs/*/internals/09-development.md`.
- **R-REL-2.** Если команда держит зеркало на внутреннем Bitbucket, теги должны зеркалироваться
  тоже — это сказано в документации по установке.

## 6. Проверка

- `node --test`, `validate-skills`, `check-tokens` — зелёные; CI на Windows, Linux, macOS.
- Тест на временном git-репозитории как remote: теги `v0.3.0`, `v0.4.0` → уведомление;
  недоступный remote → тишина и запись ошибки в кэш; таймаут не задерживает `SessionStart`.
